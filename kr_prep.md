# Подготовка к Контрольной работе №1 (Git & DevOps)

## 1. Когда я выберу rebase, а когда merge? Почему?
- **Выбор `git rebase`**:
  Используется при работе в локальных изолированных feature-ветках для подтягивания актуальных изменений из `main` (`git checkout feature && git rebase main`) перед созданием Pull Request, а также для локального "причёсывания" истории коммитов (`git rebase -i`).
  *Причина:* Обеспечивает чистую, строгую линейную историю коммитов без мусорных промежуточных merge-коммитов ("железных дорог"). В такой истории легко проводить аудит через `git log`, искать баги через `git bisect` и делать `git cherry-pick`.
- **Выбор `git merge`**:
  Используется при слиянии готовых веток в общие стабильные ветки (например, слияние pull request в `main`, `master`, `release`), а также при интеграции изменений между публичными ветками, где работают несколько разработчиков.
  *Причина:* Сохраняет истинную хронологическую историю параллельной разработки со всеми авторами и временными метками, не переписывает хеши коммитов и является полностью безопасным для совместной работы.

## 2. Что произойдёт, если я сделаю rebase публичной ветки, с которой работают коллеги?
- Команда `git rebase` буквально пересоздаёт коммиты с новыми SHA-1 хешами (даже если изменения те же самые).
- Если публичная ветка уже была отправлена на сервер (`push`), то после rebase локальная и удалённая ветки разойдутся. При попытке запушить Git выдаст ошибку, требуя force push (`git push --force`).
- Если сделать `--force`, история на сервере перетрётся. У всех коллег, которые успели стянуть старую версию ветки или создали от неё свои дочерние ветки, локальное состояние рассинхронизируется. При следующем `git pull` у них возникнет каша из дублирующихся коммитов (старых и новых), бесконечные ложные merge-конфликты, и история проекта будет испорчена.
- **Золотое правило Git:** *Never rebase public branches!* Rebase допустим только для личных, нерасшаренных веток.

## 3. Зачем нужен multi-remote и в каких реальных сценариях он применяется?
`multi-remote` — это настройка нескольких удалённых репозиториев в одном локальном Git-проекте.
Реальные сценарии применения:
1. **Forking Workflow (Open Source и корпоративные проекты):**
   - `origin` — личный форк разработчика, в который отправляются ветки и создаются PR.
   - `upstream` — официальный родительский репозиторий проекта, откуда подтягиваются актуальные изменения всей команды (`git pull upstream main`).
2. **Зеркалирование и бэкап (High Availability / Disaster Recovery):**
   - Синхронный или резервный пуш сразу в несколько провайдеров (например, GitHub + GitLab / Gitverse). Если один сервис недоступен или заблокирован, работа команды продолжается без простоя на зеркале.
3. **Разделение внутренней разработки и внешнего релиза (Multi-cloud / Multi-tenant):**
   - Один remote указывает на закрытый внутренний контур (GitLab в корпоративной VPN), а второй remote — на открытый публичный репозиторий для клиентов (GitHub / Gitverse).
